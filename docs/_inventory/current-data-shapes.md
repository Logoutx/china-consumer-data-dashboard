## Data oddities

Programmatically detected by `detect_oddities()` in extract_shapes.py -- re-run the script to reproduce these rather than trusting this list after the source files change.

1. **zero_observation_series** (retail) -- Declared in retail.series with name/group/unit metadata, but no record's metrics.<id> ever carries a non-null value. A migration script that assumes every declared series has >=1 observation will mis-handle these.
   - Series: `books_magazines`
2. **missing_calendar_periods_in_records** (retail) -- 21 periods within 1985-01..2026-05 have no record at all in retail.records (not just null metrics -- the whole record is absent). Lines up with years where NBS's Jan/Feb combined-reporting convention was encoded as 'no separate record' rather than 'record with null retail_total' (compare with the flagship_series_internal_nulls finding for retail_total, which is the same convention encoded the other way in later years).
   - 21 missing within 1985-01..2026-05 (cadence assumed: monthly); sample: `['2012-01', '2012-02', '2013-01', '2013-02', '2014-01', '2014-02', '2015-01', '2015-02', '2016-01', '2016-02', '2017-01', '2017-02', '2018-01', '2019-01', '2020-01']`
3. **missing_calendar_periods_in_records** (income) -- 6 periods within 2013-12..2026-03 have no record at all in income.records (not just null metrics -- the whole record is absent). Matches income.coverage_note: 2013-2015 is an annual-only historical-supplement layer, so the intervening quarters genuinely never existed as separate releases.
   - 6 missing within 2013-12..2026-03 (cadence assumed: quarter_end_months); sample: `['2014-03', '2014-06', '2014-09', '2015-03', '2015-06', '2015-09']`
4. **flagship_series_internal_nulls** (retail) -- retail.records exist for these periods but metrics.retail_total has no non-null value.

6. **record_schema_evolution** (retail) -- retail.records is not one uniform shape -- 3 distinct key-sets coexist (see records_summary.record_key_signatures for exact counts/keys). **Chart-mode / revision-variant logic app.js expects:**
- `version`: state.version in {latest, published} -> selects published_month_* vs latest_month_*/month_* fields
- `mode`: state.mode in {value, yoy, trend} -> trend is property-price only, client-computed chained index
- `retailFrequency`: state.retailFrequency in {period, ttm} -> ttm is a client-computed 12-point rolling sum, NOT stored in data
- `incomeFrequency`: state.incomeFrequency in {quarter, ttm, annual} -> ttm is a client-computed 4-point rolling sum over quarterly deltas
- `incomeScale`: state.incomeScale in {percapita, national} -> national multiplies by hardcoded populationWan table in app.js, only when seriesUnit === '元'
- `propertyCity`: state.propertyCity in {overall, core, capitalNewTier, other} -> groups drawn from data.property.cities plus hardcoded city-group lists in app.js
- `TTM_note`: TTM is never a stored flag on a series; it is always a client-side rolling-window computation (window=12 for retail, window=4 for income quarterly points).
- `revision_variant_note`: retail.versioning_note (verbatim): 每个指标保留 latest_*（当前最新版本）与 published_*（发布日期版本）。month_* 字段保留为 latest_* 的兼容别名。
